# 커맨드 완료 4줄 블록 — 스펙

> 상태: **스펙만. 아직 아무 커맨드도 이 블록을 렌더하지 않는다.**
> 이 웨이브(T-48)의 수락 조건은 "블록이 보인다"가 아니라 **"커맨드 출력이 한 바이트도 변하지 않았다"** 이다.
> 그 증명은 `tests/firewall/command-output-invariance.test.js` 가 들고 있다.
> 캐리어 목록·블록 리터럴의 기계 판독 정본은 `schemas/completion-block-carriers.json` 이다 —
> 이 문서와 그 파일이 어긋나면 게이트가 레드가 된다.

## 1. 무엇을 고치는 스펙인가

진행률 바가 `100%` 에 닿는 순간, 지금 사용자가 읽는 뜻은 **"끝났다"** 이다.
설계 §33 은 그 등식을 깬다:

```text
100% = Execution Progress Complete
```

실행이 끝난 것이지 **미션이 수락된 것이 아니다.** 미션 수락은 별개의 네 가지가 모두 서야 성립한다:

```text
Progress 100% + Tasks Resolved + Current Plan
+ Fable 5.1 Review PASS + Verification PASS
+ No Critical Finding + Outcome Persisted
= MISSION COMPLETE
```

그래서 100% 바 하나로 런을 끝내면 **검수·검증·영속화를 건너뛴 런과 통과한 런이 화면에서 같아 보인다.**
4줄 블록은 그 둘을 눈으로 구분시키는 장치다.

## 2. 렌더 순서 (정본: 설계 §33)

① 기존 진행률 바가 100% 에 닿는다 — **템플릿 무변경.** `commands/team.md` 의
"Phase 3.5 진행률 렌더링" 박스 그대로(40칸 `━` 괘선, 20칸 `█`/`░` 바).

② 이어서 두 줄:

```text
Execution complete.
Running independent review...
```

③ 독립 검수가 끝난 뒤 4줄 블록 + 종결 줄:

```text
Execution     ✓ 100%
Review        ✓ Fable 5.1 PASS
Verification  ✓ PASS
Outcome       ✓ Saved

✓ MISSION COMPLETE
```

라벨 열은 **14칸 좌측 정렬**(`Execution`+공백5 = `Verification`+공백2 = 14). 체크마크는 `✓`(U+2713).

④ 그 뒤 Final Scorecard(설계 §34). 스코어카드는 `outcome.md` 생성과 **같은 트리거**다 —
파일이 없으면 스코어카드도 없다(설계 §3.4). 스코어카드를 못 그린다고 4줄 블록을 생략하지는 않는다.

## 3. 4줄은 상태이지 장식이 아니다

각 줄은 **판정을 싣는다.** `✓` 를 무조건 찍으면 블록 전체가 의미를 잃는다.
실패·미측정 상태를 표시할 자리가 없으면 이 블록은 fail-open 이다 — 렌더 웨이브는 아래를 반드시 정한다.

| 줄 | 참이려면 | `✓` 가 아닐 때 |
|---|---|---|
| `Execution` | 배정 작업 단위가 전부 종료(성공·실패 무관) | 렌더하지 않는다 — 아직 실행 중이다 |
| `Review` | 독립 검수가 PASS 를 반환 | 실패·미실시를 **글자로** 적는다. 공백이나 `✓` 로 두지 않는다 |
| `Verification` | 검증 파이프라인 PASS | 같음 |
| `Outcome` | 결과가 파일로 남았다(`outcome.md`) | 같음 |

`✓ MISSION COMPLETE` 종결 줄은 **네 줄이 전부 `✓` 일 때만** 찍는다.
하나라도 아니면 종결 줄을 생략한다 — 이 블록의 존재 이유가 바로 그 구분이다.

## 4. 캐리어 (3개 — 실측 기준)

정본은 `schemas/completion-block-carriers.json#carriers`.

| 파일 | 진행률 바 | 설계 명시 | grep 도출 | 블록이 붙을 지점 |
|---|---|---|---|---|
| `team.md` | **리터럴**(리포 유일 원본) | O | O (M1~M7) | Phase 5 최종 100% 바 직후 |
| `autopilot.md` | 참조(team.md 를 가리킴) | O | O (M2·M7·M8) | ★ 최종 진행률 100% 렌더 직후 |
| `split.md` | **없음** | O | **X (전 마커 0건)** | `integrate` 배치 랜딩 성공 직후 |

**도출 규칙**: 설계가 이름으로 명시했거나, 진행률 바를 실제로 렌더한다고 마커 스캔으로
도출된 파일만 넣는다. 둘 중 어느 쪽으로도 도출되지 않으면 **넣지 않는다.** 추측으로 채우지 않는다.

**마커 스캔 실측** (분모 `commands/*.md` 79개, 2026-09-02T07:25:22Z):

| 마커 | 히트 |
|---|---|
| M1 `📊 작업 진행률` | `team.md` |
| M2 `🎉 작업 완료` | `autopilot.md`, `team.md` |
| M3 `✅ 완료 {done} / 전체 {total}` | `team.md` |
| M4 `└ 현재 단계:` | `team.md` |
| M5 괘선 `━`×40 | `team.md` |
| M6 바 `█`×20 | `team.md` |
| M7 `render-progress.js` | `autopilot.md`, `team.md` |
| M8 `Phase 3.5 진행률 렌더링` | `autopilot.md` |

`autopilot.md` 는 M1 리터럴이 없다 — 템플릿을 복제하지 않고 `team.md` 를 참조하기 때문이다.
M2·M7·M8 로 렌더 경로임이 도출된다. 사본이 하나뿐이라 **캐리어 간 "바이트 동일" 비교는 성립하지 않는다.**

### 설계의 "5" 와 실측 "3" 의 차이 — `unresolved` 2건

설계는 `team.md`·`autopilot.md`·`split.md` **3개만 이름으로 적고** "5캐리어" 라 쓰며, 같은 문장이
캐리어 집합을 *"보고 계약과 같은 parity 게이트 대상"* 이라 규정한다. 그 게이트
(`tests/commands/report-contract-parity.test.js`)의 `CARRIERS` 는 5개다.

남는 2개는 **버리지 않고** 레지스트리의 `unresolved` 에 이름을 달아 남긴다.

| | parity CARRIERS | 캐리어 | `unresolved` |
|---|---|---|---|
| `team.md` | O | O | |
| `autopilot.md` | O | O | |
| `split.md` | O | O | |
| `sc.md` | O | | **O** |
| `ultraplan.md` | O | | **O** |

**사유(둘 동일)**: ① 설계가 이름으로 명시하지 않았고 ② 진행률 바 마커 **M1~M8 전건 0건**이다.
캐리어인지 아닌지 판단할 근거가 없어 캐리어로 넣지 않았다 — **추측으로 채우지 않는다.**

**둘은 같은 등급이다.** 한쪽만 캐리어로 올리려면 다른 한쪽도 같은 근거가 필요하다 —
한쪽만 올리는 것은 근거가 아니라 선호다. 게이트가 이를 강제한다:
캐리어 3 + `unresolved` 2 = parity 5 를 **등식**으로 고정하고, `unresolved` 2건이 실제로
마커 0건인지를 **매 실행 재측정**한다. `sc.md` 가 나중에 진행률 바를 갖게 되면
그 어서션이 레드가 되고, 그때 `unresolved` 에서 캐리어로 올리는 것이 정답이다.

### `split.md` 의 모순 (해소하지 않음)

`split.md` 는 설계가 이름으로 명시했는데 **전 마커 0건**이다. 진행률 바를 아예 렌더하지 않는다.
완료 신호가 퍼센트가 아니라 `Split-Limb` git 트레일러 표이기 때문이다. 설계 명시와 실측이 이렇게
어긋나는데, 어느 쪽이 옳은지는 이 웨이브에서 정하지 않았다.

## 5. 렌더 웨이브가 먼저 답해야 하는 것

이번 웨이브에서 **풀지 않았다.** 답 없이 렌더하면 블록이 거짓말을 한다.

1. **`split.md` 의 `Execution ✓ 100%` 는 무엇으로 채우나.** split 의 완료 신호는 퍼센트가 아니라
   `Split-Limb` git 트레일러 표다. 줄기 5개 중 3개만 `done` 인 상태에 100% 를 찍으면 안 된다.
2. **캐리어가 3개가 맞는가 5개가 맞는가.** 설계는 "5" 라 쓰고 실측은 3이다(§4).
   `sc.md`·`ultraplan.md` 를 넣기로 했다면 둘 다 진행률 바가 없으므로 종료 지점을 새로
   정해야 하고, `sc.md` 는 라우터라 대상 커맨드가 이미 찍은 블록 위에 **두 번째 블록**을
   얹을 수 있다.
3. **`Review ✓ Fable 5.1 PASS` 의 모델명.** 설계 원문은 `Fable 5.1` 이다. 그런데 모델 ID 를 문서·프롬프트에
   하드코딩하지 말라는 규칙이 있고 정본은 `lib/core/model-policy.js#resolveModel` 이다. 리터럴을 박을지
   실제 검수 모델을 주입할지 미결.
4. **`Verification` 의 판정원.** `/verify` 파이프라인인지 태스크별 `verification` 명령인지 미결.

## 6. 알려진 드리프트 (D1) — 고치지 않았다

완료 박스 2행 꼬리말의 **두 리터럴 사본이 서로 다르다.**

| 사본 | 꼬리말 |
|---|---|
| `commands/team.md` | `(전 작업 검수 통과)` |
| `scripts/render-progress.js` | `(전 작업 완료)` |

측정 시각 2026-09-02T07:12:21Z. 뜻도 다르다 — **"검수 통과"는 리뷰 결과 주장이고 "완료"는 실행 사실 주장**이라,
같은 자리에서 서로 다른 것을 약속한다. 어느 쪽으로 통일할지는 오너 판단이므로 여기서 정하지 않았고,
두 파일 모두 T-48 의 소유 밖이라 손대지 않았다. 게이트는 **이 차이를 현재 값 그대로 고정**해
조용히 더 벌어지는 것만 막는다.

## 7. 설계 삽화와 라이브 규격의 불일치

설계 §33 의 UI 목업은 **괄호로 감싼 32칸 바**(`[████…] 100%`)를 쓴다. 라이브 캐리어는
**괄호 없는 20칸 바**다. **라이브를 유지한다** — §33 의 바는 4줄 블록의 선행 조건을 보이려는 삽화이지
바 규격 변경 지시가 아니고, T-48 은 출력을 바꾸지 않는다.

## 8. 이 스펙이 보증하지 않는 것

- **아무도 이 블록을 렌더하지 않는다.** 이 문서는 글이다. 글 ≠ 배선 ≠ 실행 ≠ 결과.
- **캐리어 목록이 완전하다는 보증이 아니다.** 설계는 "5", 캐리어는 3, `unresolved` 가 2 이고
  그 2건은 미확인이다(§4). 게이트 그린은 그 차이가 **기록됐다**는 뜻이지 해소됐다는 뜻이 아니다.
  마커 스캔은 **마커를 가진 파일**만 찾는다 — 진행률 바를 다른 문구로 렌더하는 커맨드가
  있으면 M1~M8 어느 것에도 안 걸리고 이 문서는 그것을 모른다.
- **`split.md` 가 캐리어라는 보증이 아니다.** 설계 명시만 있고 전 마커 0건이다(§4).
- **§3 의 실패 표시 규약은 아직 어떤 코드로도 강제되지 않는다.** 렌더 웨이브가 `✓` 를 무조건 찍어도
  현재 게이트는 잡지 못한다.
